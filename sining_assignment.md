## Part 1 — Topic 6: Window-to-Viewport Mapping

Window-to-viewport mapping as a formal concept in computer graphics appeared in the early literature of interactive graphics systems during the 1970s, emerging alongside the broader development of structured graphics pipelines and coordinate abstraction frameworks. The specific problem that motivated this concept was one of fundamental mismatch between the mathematical world that a graphics application describes and the physical world of the display hardware on which it must be rendered. A computer program working with geometric or scientific data might define shapes, curves, and points using any coordinate system whatsoever, perhaps a coordinate system where one unit represents a kilometer and the scene spans from negative ten thousand to positive ten thousand in both dimensions, or perhaps a coordinate system where one unit represents a nanometer and the shapes of interest occupy a region from zero to one in both dimensions. The physical display monitor, by contrast, has a fixed number of pixels, perhaps eight hundred across and six hundred down, and the graphics hardware expects all coordinates that will actually appear on screen to be expressed in terms of these pixel positions. Bridging this gap, allowing the application programmer to describe the world in natural, problem-appropriate coordinates while the graphics system handles the translation to physical screen coordinates, was precisely the problem that window-to-viewport mapping was designed to solve.

The terminology that became standard in the literature distinguishes between two regions. The window is a rectangular region defined in the application's own world coordinate system, representing the portion of the mathematical world that the programmer wishes to display. The viewport is a rectangular region defined in the physical screen coordinate system, representing the area of the screen into which the selected portion of the world will be drawn. The mapping between the two is a two-dimensional linear transformation that scales and shifts coordinates so that a point at the left edge of the window maps to the left edge of the viewport, a point at the right edge of the window maps to the right edge of the viewport, and similarly for the top and bottom edges. Any point inside the window maps to a corresponding point inside the viewport, with the relative position of the point within the window preserved exactly in the viewport.

The mathematical derivation of this mapping appears in early textbooks on computer graphics, most notably in the foundational work by Newman and Sproull, whose textbook Principles of Interactive Computer Graphics published in 1973 was among the first to treat this topic systematically. The derivation follows from the requirement that the transformation be linear and that it map the four corners of the window exactly to the four corners of the viewport. If the window spans from a minimum x-coordinate to a maximum x-coordinate in world space, and the viewport spans from a minimum x-coordinate to a maximum x-coordinate in screen space, then the scaling factor in the x-direction is the ratio of the viewport width to the window width, and the translation in the x-direction is whatever offset is needed after scaling to align the left edge of the window with the left edge of the viewport. An identical calculation applies independently in the y-direction. The result is a pair of simple linear equations, one for each coordinate dimension, that together define the complete window-to-viewport transformation.

The significance of this mapping extended well beyond simple convenience. Before it was formalized, programmers working with graphics systems had to manually compute screen coordinates from their problem coordinates in every piece of code that generated output, scattering conversion arithmetic throughout their programs and making it difficult to change the portion of the world being displayed or the size of the display region without modifying code throughout. The window-to-viewport abstraction collected all of this coordinate transformation logic into a single, reusable mechanism that the graphics system applied automatically. This meant that an application could zoom in on a particular region of the world simply by narrowing the window boundaries without touching any of the code that generated geometric output, and could resize or reposition the display area simply by changing the viewport boundaries. These capabilities, which feel completely natural today, were genuine advances in software design when they were first introduced.

The concept also provided the foundation for multiple simultaneous views of the same world data, a capability that became essential in computer-aided design and scientific visualization. By defining multiple viewports on the same physical screen, each with its own associated window in world space, a single program could display the same geometric model from different angles, at different scales, or with different subsets of the data visible, all without requiring separate copies of the underlying geometric description. This multi-viewport capability, made straightforward by the window-to-viewport abstraction, shaped the interface design of technical graphics software for decades.

My own encounter with window-to-viewport mapping came during a graphics programming course when I was studying the mathematics of coordinate transformations, and I remember that it initially felt like a simple and almost obvious idea. The basic algebra is not difficult, and the geometric intuition behind it is straightforward. What took longer to appreciate was the elegance and practical importance of the abstraction. When I first implemented a small graphics program that used world coordinates, I noticed how naturally I could zoom and pan simply by adjusting the window boundaries, without changing any of the code that described the shapes. That experience, seeing the mapping work in practice, was what transformed my understanding from knowing the formula to genuinely appreciating why the concept mattered.

The aspect of the implementation that required the most careful thought was handling the case where the aspect ratio of the window, meaning the ratio of its width to its height in world coordinates, does not match the aspect ratio of the viewport in screen coordinates. When these ratios differ, the transformation applies different scaling factors in the x and y directions, which causes circular objects to appear as ellipses and square objects to appear as rectangles. Deciding whether to allow this distortion or to enforce uniform scaling by padding the viewport with empty space on one side requires a design decision that depends on the application. Scientific visualization typically requires undistorted mapping so that shapes appear with their correct proportions, while some display applications might prefer to stretch the image to fill the available viewport space. Understanding this trade-off and knowing how to compute the appropriate adjustment was an important practical lesson.

The way I picture the window-to-viewport mapping in my mind is as a kind of zooming and panning operation applied to an infinite mathematical canvas. I imagine the world coordinate space as a vast flat plane extending infinitely in all directions, with the shapes and objects of interest drawn somewhere on that plane in whatever scale and position the application has chosen. The window is like a rectangular picture frame that I can place anywhere on this infinite canvas, at any size, selecting the portion I want to see. The viewport is a fixed rectangular area on the physical screen, like the screen of a digital picture frame. The window-to-viewport mapping is the mechanism that takes whatever falls within the canvas frame and stretches or compresses it to fit the screen frame, so that the contents of the canvas frame appear correctly within the screen frame. Moving the window left or right corresponds to panning the view across the canvas. Shrinking the window corresponds to zooming in, because a smaller window region gets stretched to fill the same screen area. Enlarging the window corresponds to zooming out.

Now, if I were to explain window-to-viewport mapping to someone with no engineering or programming background, I would use the example of framing a photograph, because the analogy is almost perfect. Imagine you have a very large photograph, perhaps a panoramic landscape photograph printed on a long roll, showing a wide scene from left to right. You also have a picture frame of fixed size that you want to use to display a portion of this photograph on your wall. The window-to-viewport mapping is the process of deciding which portion of the photograph to show in the frame and then scaling that portion so it fills the frame completely.

If you hold the frame up to the left side of the panorama, you see the leftmost portion of the landscape, scaled to fill the frame. If you slide the frame to the right, you see a different portion of the landscape. If you move the frame closer to the photograph, the frame covers a smaller area and the details in the selected region appear larger and more magnified. If you move the frame farther away, the frame covers a wider area and more of the landscape is visible, though in less detail. In all cases, what appears in the frame is the portion of the photograph that the frame selects, scaled to fit the frame's dimensions. The photograph itself never changes. Only the frame's position and distance determine what you see.

In a computer graphics system, the photograph is the entire mathematical world that the program has described in world coordinates. The frame is the window, which selects a portion of that world. The fixed rectangular area on the computer screen is the viewport, which is like the picture frame hanging on the wall. The window-to-viewport mapping is the mathematical operation that scales the selected portion of the world to fit the screen area, just as physically printing a crop of the photograph to fill a frame would scale that selected region. The programmer can move the window to look at different parts of the world, resize the window to zoom in or out, and the mapping ensures that whatever falls within the window is correctly displayed within the viewport on screen.

This framing analogy also naturally explains the aspect ratio problem. If the picture frame is square but the selected portion of the photograph is rectangular, you have to decide whether to stretch the image to fill the square frame, distorting the proportions of everything in the image, or whether to show the image at its correct proportions and leave empty borders at the top and bottom of the frame. Both choices are valid for different purposes, and the same choice arises in the window-to-viewport mapping whenever the window and viewport have different proportional shapes.

Window-to-viewport mapping, despite its mathematical simplicity, represents one of the most practically important abstractions in the history of computer graphics software. It cleanly separates the problem domain from the display hardware, allowing programmers to think in whatever coordinate system is natural for their application while delegating to the graphics system the work of translating that natural representation into the physical pixel positions that the hardware requires. This separation of concerns made interactive graphics programming dramatically more productive and laid the conceptual groundwork for the hierarchical coordinate transformation systems that underlie all modern graphics pipelines.

## Part 2 — Topic 2: 2D Platformer Video Game Engine

A two-dimensional platformer video game engine is a software system that must simultaneously manage many interrelated tasks: keeping track of where the player's character is within a potentially enormous level, deciding which portions of that level are actually worth rendering in any given frame, determining when the character's body overlaps with enemies or terrain in a way that triggers a game event, and presenting the character's movement and actions through smooth and believable animated sequences. Each of these tasks draws on specific computer graphics concepts in ways that are not immediately obvious but that fundamentally determine whether the game feels fluid, responsive, and visually convincing or feels sluggish, choppy, and disorienting.

The first major challenge is what game developers call camera tracking or world scrolling, and it is intimately connected to the concept of window-to-viewport mapping. A typical two-dimensional platformer level is far larger than the screen can display at once. A level might extend for thousands of pixels horizontally and hundreds of pixels vertically, representing a world that would require many screens of space to display in its entirety. The player's character occupies only a small region of this large world and moves through it continuously. The camera, meaning the portion of the world that is currently being shown on screen, must follow the character so that the player can see where they are going and react to what lies ahead.

This camera tracking is implemented through a dynamic window-to-viewport mapping. The world is described in world coordinates that span the full extent of the level. The camera defines a rectangular window in these world coordinates, centered on or near the player's character. The screen is the viewport. At each frame, the engine updates the window position based on the character's current world-coordinate position, and then applies the window-to-viewport transformation to determine which screen pixel each world pixel maps to for that frame. The result is that as the character moves through the world, the window moves with them, and the viewport always shows the portion of the world immediately surrounding the character.

Smooth camera behavior requires more than simply centering the window exactly on the character at every frame. Many platformer games implement a camera that follows the character with a slight delay, called camera lag or smoothing, so that the view does not jerk abruptly when the character changes direction. This is achieved by interpolating the window position toward the character's position each frame rather than setting it exactly, so the camera gradually catches up to the character rather than instantly tracking every movement. The mathematics of this interpolation, typically a simple linear blend between the current camera position and the target position, is grounded in the same coordinate manipulation that underlies all two-dimensional geometric transformations. Additional camera behaviors, such as looking ahead in the direction of movement, snapping to predefined positions when the character enters certain zones, or locking the vertical position of the camera when the level is not taller than the screen, all involve variations on the same window position calculation.

The second major challenge is deciding which parts of the large game world to actually render in each frame, a problem closely related to clipping and culling. A large platformer level might contain thousands of tiles, dozens of enemy characters, hundreds of background decorations, and various interactive objects. Attempting to render all of them every frame would be extremely wasteful, because the vast majority are outside the camera's current window and therefore invisible to the player. The engine must efficiently identify which objects fall within the current window and render only those, discarding everything else.

This process mirrors the clipping algorithms that computer graphics researchers developed in the 1970s for exactly this purpose. For a tile-based platformer level, the engine can use the current window boundaries to compute directly which tile columns and rows are visible, without testing every individual tile. Because tiles are arranged in a regular grid, a simple division of the window coordinates by the tile size gives the index range of visible tiles immediately, making the culling operation essentially instantaneous regardless of how many total tiles exist in the level. For non-tile objects such as enemy characters and decorations, the engine tests each object's bounding rectangle against the current window rectangle using a simple overlap test and renders only those that overlap. Objects entirely outside the window are skipped entirely. Objects that partially overlap the window boundary are rendered and rely on the graphics hardware's built-in scissor clipping to remove the portions that fall outside the viewport.

This culling process is critical not only for performance but for correctness. If the engine did not cull off-screen objects, it would waste rendering time on invisible content, but more subtly, it would also need to ensure that all of the coordinate transformations for off-screen objects produced valid screen coordinates, which for objects far from the window would yield coordinate values far outside the screen boundaries. The combination of culling and clipping ensures that only geometrically relevant content reaches the rasterization stage.

The third major challenge is collision detection, which determines when the player's character overlaps with terrain, enemies, collectible items, or hazards in ways that should trigger game events such as landing on a platform, taking damage, or collecting a coin. In a two-dimensional platformer, collision detection is fundamentally a problem of geometric overlap testing between rectangles or other simple shapes, and it depends entirely on having a clear and consistent coordinate system in which all objects exist simultaneously.

The player's character and each interactive object in the level are assigned a hitbox, which is a rectangle defined in world coordinates that approximates the geometric extent of the object for collision purposes. At each frame, the engine tests whether the character's hitbox overlaps with the hitboxes of nearby objects. Because testing the character against every object in the entire level would be unnecessarily expensive, the engine typically uses a spatial partitioning structure, such as dividing the level into a grid of cells and only testing objects that share a cell with the character, to limit the number of overlap tests performed each frame.

The overlap test between two rectangles is a direct application of coordinate geometry. Two rectangles do not overlap if and only if one is entirely to the left of the other, entirely to the right, entirely above, or entirely below. Checking these four conditions using the minimum and maximum x and y coordinates of each rectangle requires only a few comparisons and can be performed thousands of times per frame with negligible computational cost. When an overlap is detected, the engine computes the depth and direction of the overlap, meaning how far and in which direction the character has penetrated the colliding object, and uses this information to resolve the collision by pushing the character back to a non-overlapping position or by triggering the appropriate game event.

The precision of the coordinate system used for collision detection matters significantly for gameplay quality. If world coordinates are represented with insufficient precision, the character may appear to collide with terrain when visually it seems to be clear, or may pass through thin platforms, producing the frustrating tunneling problem where fast-moving objects skip past thin barriers entirely because they move more than the barrier's thickness in a single frame. Modern platformer engines address tunneling by performing swept collision tests that check for overlaps not just at the character's current position but along the entire path the character traveled during the frame, ensuring that no collision is missed regardless of how fast the character moves.

The fourth major challenge is animation, and specifically the rendering of smooth, convincing transitions between different animated states of the player's character. In a two-dimensional platformer, the character is typically represented as a sprite, which is a small rectangular image drawn at the character's current world-coordinate position. The character has multiple animated sequences for different actions: standing idle, running left or right, jumping, falling, attacking, taking damage, and so on. Each animated sequence consists of a series of individual sprite frames that are cycled through at a fixed rate to create the illusion of motion.

Managing animation in a platformer engine requires tracking the current animation state of the character, the current frame within that animation, and the elapsed time since the current frame began. At each game update, the elapsed time is incremented, and when it exceeds the duration of the current frame, the animation advances to the next frame. When the character's action changes, for example when a running character begins to jump, the engine transitions from the running animation to the jumping animation. The quality of this transition determines whether the animation feels smooth and natural or abrupt and jarring.

The visual rendering of a sprite frame draws on the same coordinate transformation concepts that underlie the entire two-dimensional rendering pipeline. The sprite image is defined in a local coordinate system centered on the sprite, and the engine applies a two-dimensional transformation that translates the sprite to the character's current world-coordinate position, potentially scales it to handle horizontal mirroring when the character faces left rather than right, and then applies the window-to-viewport mapping to convert the result to screen coordinates. Horizontal mirroring is implemented as a scaling transformation that multiplies the x-coordinates of the sprite by negative one, effectively reflecting the image across the vertical axis, which allows a single set of right-facing animation frames to serve as both the right-facing and left-facing animations without requiring duplicate artwork.

The rendering of multiple sprites at different depths in the scene, such as the player character, foreground objects, and background layers, requires a consistent approach to draw order. In a two-dimensional scene without a depth buffer, the visual appearance of depth is achieved entirely by controlling which sprites are drawn first. Sprites drawn earlier are overwritten by sprites drawn later, so drawing background layers first and foreground elements last ensures that foreground content appears in front of background content. Many platformer games also implement multiple scrolling background layers that move at different speeds as the camera moves, a technique called parallax scrolling. Each background layer uses its own window-to-viewport mapping with a different scaling factor for the window offset, so that distant background layers appear to move more slowly than the foreground, creating a convincing illusion of depth despite the fundamentally two-dimensional nature of the scene.

The smooth rendering of animated sprites also depends on careful management of the sprite coordinate transformation when the character is in motion. If the character's screen position is computed by converting the world-coordinate position directly to screen coordinates, the character will appear to snap between adjacent pixel positions as it moves, producing visible stuttering unless the character's movement speed happens to be an exact integer number of pixels per frame. Modern platformer engines store world-coordinate positions as floating-point numbers and apply the coordinate transformation to produce fractional screen positions, then round to the nearest pixel only at the final rendering step. This sub-pixel accuracy in the underlying coordinate representation ensures that motion appears smooth even when the character moves at fractional pixel speeds per frame.

Taken together, the window-to-viewport mapping that implements camera tracking, the clipping and culling that restrict rendering to the visible portion of the world, the coordinate-based overlap testing that implements collision detection, and the sprite transformation and draw order management that implements animation together form the complete computational foundation of a two-dimensional platformer engine. Each of these techniques is grounded in specific computer graphics concepts that researchers developed over decades to address fundamental problems of representing, transforming, and displaying geometric content on raster displays. The platformer game engine is, in this sense, an applied demonstration of classical computer graphics theory, showing how abstract mathematical ideas about coordinate transformations, clipping, and rasterization translate directly into the concrete, interactive, and visually engaging experience of playing a game.
